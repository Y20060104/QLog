# ADR-002：尾端锚定帧头与连续回绕载荷

- 状态：已接受
- 日期：2026-08-16
- 取代：ADR-001 中的 V1 生产布局

## 背景

ADR-001 允许载荷（payload）跨越 SPSC 环形缓冲区的物理末端进行拆分。该布局能够使用全部容量，但它会使生产者编码变为双区间操作，并且要求消费者先将回绕字符串线性化，fmt 才能使用它们。

V1 倾向于在队列两端都使用更简单的连续载荷。BQLog 的 SISO 环形缓冲区展示了一个有用的思路：将记录元数据留在当前尾端位置，把尾端剩余区域计入该记录，并将载荷放在环形缓冲区的物理起始处。QLog 采用这一布局思路，但使用自己的基于字节的协议、64 位逻辑游标、标准 C++ 原子操作，以及明确的正确性和可观测性要求。

## 决策

### 固定几何布局

- 容量 `C` 是 2 的幂，并且是 8 的倍数。
- 当 `frame_bytes` 仍是 `uint32_t` 字段时，容量不大于 `2^31` 字节。
- 帧起始位置和帧大小按 8 字节对齐。
- `H` 是帧头大小，为 8 字节。
- 生产者和消费者使用 64 位逻辑字节游标。物理偏移为 `logical_cursor & (C - 1)`。
- SPSC 热路径使用普通本地游标，并在每个方向各使用一个发布原子游标。它不包含 CAS、`fetch_add`、每槽就绪状态或版本号。

帧头为：

```cpp
struct FrameHeader {
    std::uint32_t frame_bytes;   // all logical bytes consumed by this frame
    std::uint32_t payload_bytes; // exact meaningful payload size
};
```

帧头在物理上始终连续。这由三个事实保证：容量是 8 的倍数，每个帧消耗的字节数是 8 的倍数，并且帧头本身是 8 字节。

### 布局计算

对于载荷大小 `P` 和逻辑写游标 `W`：

```text
offset = W & (C - 1)
tail   = C - offset
normal = align_up_8(H + P)

if normal <= tail:
    header_offset     = offset
    payload_offset    = offset + H
    frame_bytes       = normal
    tail_waste_bytes  = 0
else:
    header_offset     = offset
    payload_offset    = 0
    frame_bytes       = tail + align_up_8(P)
    tail_waste_bytes  = tail - H
```

在回绕情况下，逻辑帧覆盖尾端帧头、该帧头之后未使用的尾端字节，以及物理起始处的载荷和对齐填充。因此，下一个帧紧接在起始处已对齐载荷之后开始。

不会发布单独的填充帧。禁止在不将尾端区域计入当前帧的情况下跳过它，因为消费者可能会把陈旧的尾端字节解释为新帧头。

### 准入与发布

- V1 默认使用 `C = 64 KiB`，并将载荷限制为 8 KiB。
- 配置后的环形缓冲区必须满足 `C >= 2 * align_up_8(max_payload_bytes)`。这保证每个允许的载荷在每个已对齐帧位置都有有效的连续布局。64 KiB/8 KiB 的默认值以充足余量满足此条件。
- 在任何写入之前都要检查布局计算结果。`frame_bytes` 必须不大于 `C`；否则，未来采用非常小的环形缓冲区或非常大载荷的配置，可能在某个特定游标位置没有有效的连续放置方式。
- `try_reserve()` 接收最终、精确的载荷大小。`commit()` 不能缩小该大小：在已经选择载荷地址之后，更改大小可能会使记录从回绕布局变为普通布局。
- 一个通道上最多只能有一个尚未完成的生产者预留。
- 生产者根据其缓存的消费者游标计算可用空间。如果缓存值表明空间不足，它会以 acquire 语义加载一次发布读游标并重新计算。如果实际的 `frame_bytes` 仍无法放入，它将返回 `full`，并保持所有游标不变。
- 首先写入载荷。随后，`commit()` 将帧头复制到其尾端位置，使本地写游标前进 `frame_bytes`，并以 release 语义存储发布写游标。提交标记是发布游标，而不是帧头中的字节。
- 帧头字节通过 `memcpy` 传输；实现不会直接在字节存储上构造 `FrameHeader*`。
- 未调用 `commit()` 就被销毁的预留不会发布任何内容，也不会推进写游标。已中止预留留下的陈旧字节位于已发布范围之外，可以由下一次预留覆盖。

### 消费与回收

消费者在读取新帧之前，以 acquire 语义加载发布写游标的快照。它根据物理读偏移和 `payload_bytes` 重新计算预期布局，然后在公开视图之前要求满足以下所有条件：

- `payload_bytes` 在配置的 V1 限制以内；
- `frame_bytes` 已对齐、非零、不大于容量，并且等于重新计算出的布局大小；
- 完整的 `frame_bytes` 位于以 acquire 语义取得的发布游标快照以内。

对于普通帧，载荷紧接在帧头之后开始。对于回绕帧，载荷从物理偏移 0 开始。在两种情况下，它都是一个连续字节区间。只有在后台完成对该区间的读取后，消费者才将其本地读游标推进 `frame_bytes`。回收按照 V1 决策日志中的规定，以 release 语义分批发布。

### 内存序

```text
producer payload and header writes
    -> cursors_.write_cursor_.store(release)
    -> cursors_.write_cursor_.load(acquire)
    -> consumer header and payload reads

consumer completes all reads from the frame
    -> cursors_.read_cursor_.store(release)
    -> cursors_.read_cursor_.load(acquire)
    -> producer may reuse those bytes
```

陈旧的对端缓存游标只能使生产者或消费者采取更保守的行为。它们绝不能扩大可写或可读范围。

## 后果

### 优点

- 生产者编码始终以一个连续载荷区间为目标。
- 消费者解码和 fmt 格式化始终读取一个连续载荷区间。
- 回绕记录不需要暂存缓冲区，也不需要对每个字段进行拆分处理。
- 普通的非回绕路径保留与双区间设计相同的游标操作和原子操作。

### 代价

- 一个回绕帧会消耗 `tail - H` 个内部碎片字节。
- 在高占用率下，更大的回绕 `frame_bytes` 可能导致双区间布局本可避免的准入失败。
- 接近环形缓冲区容量的载荷可能在某些偏移处没有有效的连续回绕布局。V1 的 8 KiB 载荷和 64 KiB 默认容量留有充足余量，但实现仍必须验证这一条件。
- 该设计预期会减少回绕记录的 CPU 工作；在对比基准确认生产者尾延迟、消费者吞吐量和丢弃行为之前，不会宣称它在整体上更快。

## 考虑过的替代方案

### 将载荷拆分到两个区间

这会保留全部容量，并继续作为 ADR-001 的基准候选方案。它不是 V1 的生产布局，因为它会使编码复杂化，并要求消费者为通用字符串格式化执行线性化。

### 发布单独的填充帧或无效帧

这会使下一个载荷保持连续，但会增加一个逻辑记录和一个消费者分支。如果要跳过字节，就必须使用填充标记；静默跳过字节是不正确的。所选布局改为把未使用的尾端字节计入真实的回绕帧，因此不需要额外标记。

### 空环形缓冲区接近尾端时重置游标

这需要生产者/消费者协调，并削弱简单的单调游标证明。V1 拒绝采用此方案。

## 必需的测量

使用相同的编码和消费者工作对比 ADR-002 与 ADR-001。至少报告：

- 生产者 P50/P99/P99.9 延迟；
- 消费者吞吐量和端到端排空吞吐量；
- attempted、accepted、full-drop、oversize-drop 和 layout-failure 的计数；
- `wrap_count`、`tail_waste_bytes` 和双区间布局的暂存复制字节数；
- 低占用率、突发负载和持续接近满载的负载；
- 使用固定和可变记录大小的 4 KiB、64 KiB 和 256 KiB 环形缓冲区。

如果 ADR-001 能够在不违反生产者延迟目标的情况下显著减少丢弃，则可以重新评估生产方案的选择。

## 验证要求

- 在微型环形缓冲区上穷举测试每个已对齐起始偏移和载荷长度。
- 测试恰好贴合尾端、帧头位于最后 8 字节、1 字节载荷回绕、恰好占满、已满、为空、预留失败、中止、提交和复用。
- 将随机操作与基于 `deque` 的参考模型比较，并验证载荷字节和每个生产者的顺序。
- 注入接近 `UINT64_MAX` 的游标并验证无符号距离行为。
- 运行 ASan、UBSan 和 TSan 测试；在硬件可用时加入一次 AArch64 acquire/release 运行。
- 保持 `attempted == accepted + dropped`，并使丢弃原因构成完整且互不相交的分类。
