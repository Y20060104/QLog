# 普通接口延迟、组件开销与加密场景定位（2026-10-16）

## 结果

实际源码已对齐 BQLog `086f2fd8` 的 SISO 半满边界通知和普通十进制转换。GNU、原生 MSVC Debug/Release 各 44/44 回归通过。官方完整复测 12 进程、1/4 生产者各三轮、9.6 亿名义吞吐调用完成；普通接口单生产者 P50 为 QLog 95、BQLog 70 ns/条，四生产者为 110、75 ns/条。指标均为每批 20 条的平均耗时分位数。

QLog 原约 1140 ns/条的主要原因已通过复现、逐批计数、分段计时和单变量 A/B 定位为 SISO 低空间提示引发的通知频率，不是仅根据源码猜测。复制/hash 融合不是这约 1 µs 的主要来源。

## 为什么 P50 会从约 1 µs 降下来

在同一编译选项下，只替换静态库中 `record_writer.cpp.o`，得到融合前/后单变量版本；使用实际上游 write-thread-cost 普通接口测试。

| 未插桩单次复现 | P50 ns/条 |
| --- | ---: |
| QLog 融合前 | 1182.7 |
| QLog 融合后 | 1152.3 |
| BQLog 普通接口 | 56.9 |
| QLog 融合后，只采用 BQLog 新半满通知规则 | 108.2 |

另外三轮短间歇负载中，融合前后仍在约 1.1–1.2 µs；连续调用时 QLog P50 约 87–93 ns。复现使用 steady_clock，排除了普通接口单位换算和偶然墙钟跳变。原库的 Release 优化和 NDEBUG 均有效。

独立计数副本取 3000 批并去掉初始 100 批，共 58000 次调用：

| 计数项 | 原通知规则 | 参考边界通知规则 |
| --- | ---: | ---: |
| HP / LP | 58000 / 0 | 58000 / 0 |
| 满 Buffer 重试 | 0 | 0 |
| 新 HP 块分配 | 0 | 0 |
| 低空间提示 | 29670 | 264 |
| 发生真实通知的批次数 | 1656 / 2900 | 264 / 2900 |
| 有通知批次比例 | 57.1% | 9.1% |

原实现只依据缓存的读游标，超过半满后持续返回提示，且不在提示点重新确认读者进度。每隔约 2 ms 再来的一批经常唤醒已经停放的 Worker。新参考仅让跨过半满边界的分配置候选提示，并 acquire 读取实际已发布的读游标，确认是否仍然半满。

```mermaid
flowchart LR
    A[缓存读游标落后] --> B[低空间提示持续为真]
    B --> C[间歇批次频繁唤醒 Worker]
    C --> D[mutex 与条件变量通知增加墙时钟耗时]
    D --> E[超过一半批次落入慢侧]
    E --> F[P50 进入微秒量级]
```

分段计时副本中，有通知批次的唤醒累计墙时钟中位约 24394 ns，即每批 20 条摊约 1220 ns；无通知批次该项为 0。全为 HP、没有重试和新分配，排除了“多数调用仍走 MISO”“每条申请新块”“满队列阻塞”为本次主要解释。

这是快/慢批次混合分布。原慢批次超过 50%，P50 进入慢侧；边界通知后慢批次降到约 9%，P50 回到快侧。P99 仍可能包含通知、调度和其他尾部事件，因此不能把 P50 改善解读为每条调用都快十余倍。

探针本身改变绝对耗时，故上述插桩分组仅用于关联和定位，正式性能采用未插桩程序。每段几十纳秒的计时含计时器开销，不逐项相加预测正常接口。一次整进程 burst CPU 采样被组间忙等主导，未用于阶段占比；Layout 使用独立纯工作负载采样。

## 十进制对齐的独立收益

固定 Record、时间戳、线程和类别，循环更改 0–1999999 的序号，复用 Layout 对象及输出缓冲，不经过 Buffer/文件/Worker。调用方目标文件相同，仅更换修改前后的库；SISO 修改在此用例中不被调用，因此这一 A/B 单独评价十进制变化。五轮交替顺序，原始输出逐字一致。

| 组件 | 修改前 QLog ns/条 | 修改后 QLog ns/条 | BQLog ns/条 |
| --- | ---: | ---: | ---: |
| 计数器 Layout | 235.528 | 94.093 | 83.208 |
| 四参数 Layout | 369.785 | 209.187 | 191.877 |

QLog 原三位表只对绝对值至少 1e9 启用；本次计数器未进入该分支。新参考对普通十进制全部使用两位查表，避免小整数逐位除法/取模后的反转。纯 Layout 采样中 `insert_integral_signed` 的自身样本占比约 49.6%→9.9%，与独立计时方向一致。浮点插入和格式扫描成为更显著的剩余工作，但占比变化不是这些函数绝对耗时增加。

毫秒前缀仍使用原三位表；其他进制、科学计数、符号和填充规则保持现有合同。新增独立 to_chars 期望值回归覆盖整数极值、10 的幂邻域、原 1e9 阈值附近、2048 组随机值及 UTF-8/UTF-16。原用户 CR 保留。

## 复制/hash 融合的验证

A/B 没有消除旧 burst 微秒级延迟。热缓存组件测试中，19 字节复制后 hash / 融合的五轮中位约 7.54 / 7.01 ns，44 字节约 10.19 / 11.33 ns，1024 字节约 70.31 / 80.68 ns。本轮不能声称融合在所有长度都更快。输入和输出工作集很小，减少一次遍历不自动减少此环境的总时间；没有进一步将差异武断归因于某条机器指令。源码保持已确认的参考实现和每后端哈希合同。

## 加密为什么可以出现不同整链吞吐

RSA/AES/Vernam 加密链保持既有对齐，本轮未修改加密生产文件。 另读取固定 78cbfbef 的 Git 对象，与参测 086f2fd8 比较，RSA/AES/Vernam 的六个原始 h/cpp 文件逐字节一致，证据为 `encryption-reference-diff.json`。逐字节 XOR 期望值与偶数次恢复校验通过；两库自动硬件分派和 AVX2/SSE 主循环已核对。

| Vernam 单次调用 | QLog ns | BQLog ns |
| --- | ---: | ---: |
| 32 字节 | 7.686 | 7.638 |
| 128 字节 | 9.690 | 9.554 |
| 1024 字节 | 22.419 | 27.601 |
| 4096 字节 | 78.186 | 94.608 |
| 65536 字节 | 1419.601 | 1458.541 |

算法对齐不强制编译产物、代码布局和运行状态相同；本轮部分块长接近，部分存在差距。它们不能直接外推为整链吞吐差距。

另在隔离副本中只对 Vernam 函数加计数和累计计时，采用普通接口、同一公钥、相同格式、1/4 生产者每线程 500000 条、明文/加密及无参/四参三轮共 48 次运行。所有 API 调用被接受；明文 Vernam 调用为零，加密调用非零，证明确实进入加密路径。四生产者 200 万条时，无参处理约 9.537 MiB，四参约 34.301 MiB，两库基本一致。Vernam 累计计时约为整批墙时钟的 0.25%–0.66%；这仅是 Vernam，不含 RSA/AES 初始化和所有文件加密管理成本。

因此旧“加密无参高 40.9%”不能解释为 Vernam 核心高 40.9%。本轮官方四生产者加密无参为 QLog 464 / BQLog 490 ms，优势约 5.6%；加密四参为 819 / 968 ms，优势约 18.2%。全链包含记录序列化、队列交接、模板缓存、编码、密钥准备、文件缓冲和 flush；剩余阶段需要各自的 A/B 才能继续分摊。
