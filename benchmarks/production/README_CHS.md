# QLog / BQLog 原生默认配置性能评测

本套件比较两个产品完成同一类文本日志业务的实际表现，保留各自实现与默认资源策略。结果范围是记录的 WSL2 主机、单进程单 Logger、普通缓冲文本文件输出。它不是同算法微基准，也不代表所有部署的生产性能。

## 入口与复现

- 测试程序：`native_benchmark.cpp`，同一业务驱动分别链接原生 QLog 和 BQLog 静态库。
- 预定方案：`plan.json`；正式执行前保存方案、源码和可执行文件哈希。
- 构建：`../../tools/prepare_production_benchmark.py`。
- 执行：`../../tools/run_production_benchmark.py`。
- 审计及统计：`../../tools/analyze_production_benchmark.py`。
- 本次原始证据：`../../docs/validation/native-production-20260920/`。
- 最终报告：`../../docs/decisions/V1_NATIVE_PRODUCTION_PERFORMANCE_20260920_CHS.md`。

已存在本次证据的工作区禁止重新构建覆盖。手动首次构建需先 `mkdir -p build`，并使用新的工作目录；完整交付包中的 `tools/reproduce_production_benchmark.py` 可以从已冻结源码建立新评测目录，避免依赖 QLog 尚未提交的工作树或 BQLog 后续版本。

## 原生实现及配置边界

| 项目 | QLog | BQLog |
|---|---|---|
| 生产入口 | `AsyncLogger::try_log`，字面量数组入口 | `log::info`，字面量数组入口 |
| 满队列策略 | 默认拒绝新记录，驱动不重试 | 默认阻塞，保持原生自适应队列 |
| 默认通道容量 | 64 KiB，每 Producer 独立 SPSC 通道 | desktop 默认 64 KiB，原生 MISO/SISO 切换及容量管理 |
| 默认文件缓存 | 256 KiB | 64 KiB |
| worker | 默认共享；指定场景独立 | 默认共享；指定场景独立 |
| 行格式 | 原生完整行、纳秒时间字段、Logger/category/tid | 原生完整行、毫秒时间字段及线程信息 |
| 时间区、滚动 | 保留产品默认 | 保留产品默认，包括原生日历滚动 |
| 测量末端完成 | `request_drain(buffered)` 并等待完成 | 原生 `force_flush()` |

文件路径和 Appender 数量属于业务配置。BQLog 配置启用 info 文件输出；QLog 使用默认等级过滤，实际业务也只产生 info。没有替换 sink、禁用格式化、缩短行前缀、包裹 write 系统调用、强制相同缓存或满队列策略。相同 `64 KiB` 数值不表示两种产品拥有相同的总内存预算。

BQLog 的 `force_flush()` 可以在调用线程参与处理尾部；QLog 由 worker 完成管理请求。计时保留这种产品差异。两者计时完成点均为库缓冲数据已交给文件写入接口，不宣称掉电持久化。驱动在计时结束后才对本试验生成的文件调用 fdatasync、逐行读取及计算 SHA-256。

## 负载、顺序及计时

1. 构造一个 Logger，记录构造耗时，启动指定数量的 Producer；首次注册和初始化包含在预热阶段。
2. 每个 Producer 先以饱和速度预热 3 秒；预热后完全排空。固定到达率场景也采用相同饱和预热，避免混入首次初始化。
3. 保持同一批 Producer 线程，屏障释放后测量 10 秒；每 256 次尝试检查截止时间，因此少量越界执行可能发生，全部计入真实分母。
4. 饱和场景循环调用，不重试被拒绝记录。固定到达率场景按每 Producer 32 条一批的计划时间投递；所有 Producer 的批次同相，属于明确的突发流量，而非均匀泊松到达。
5. 等待 Producer 结束，再完成原生排空；以测量开始至排空完成的时间计算成功输出吞吐。每个业务记录只计一次，双文件场景不把两份副本算成两条业务记录。
6. 对全部预热和测量输出逐行校验，再进行文件同步与哈希留证；这些校验和同步不计入吞吐、CPU 和 API 延迟指标。

8 个主场景覆盖小消息、浮点数加字符串混合消息、512 字节字符串、1/4/8 Producer、共享/独立 worker 和双文件 fan-out。两个到达率场景分别为总计 20 万、100 万条/秒。每个场景每库 5 次；固定种子打乱每轮场景顺序，库顺序交替。两库各做一次 60 秒混合消息持续负载测试。总计 102 次，预检不进入统计。

主场景都在一个 Logger 上执行；“独立”指该 Logger 使用独立 worker，不是每个 Producer 一个 worker。当前没有覆盖多个活跃 Logger 竞争共享 worker 的场景。

## 指标与总体倍数

`goodput = 实际接受且通过输出校验的业务记录数 / (测量开始至 Producer 结束并排空完成的秒数)`。

每一场景、每一轮组成 QLog/BQLog 配对比值。总体指数为 8 个主场景、5 轮配对比值的等权几何平均：

`G = exp(mean(log(Q_goodput / BQ_goodput)))`。

它是“本套件原生默认配置的成功输出吞吐指数”，不包含固定到达率或持续负载附加项，也不是通用的生产性能评分。饱和负载下两库能推进的业务尝试数量不同；QLog 的大量拒绝和 BQLog 的阻塞会影响各自驱动循环的 CPU 竞争，正是原生满队列策略的可见行为。

置信区间以 5 个完整重复轮次为重采样块，保留同一轮各场景的关联；精确枚举 5^5=3125 个经验 bootstrap 样本，取 2.5% 和 97.5% 分位数。单场景同样对 5 个配对值重采样。只有 5 个重复轮次，重采样假设这些块可交换，未证明轮次之间独立；区间精度有限；不做多重比较修正，不表示跨主机、跨系统或跨版本置信区间。不剔除慢试验或挑选最优次数。

单独报告以下指标，不能被一个倍数替代：

- API 接受率、拒绝数及预定到达但截止时尚未调用的请求数。
- 成功调用和拒绝调用的独立延迟直方图；每 1021 次尝试采样一次，P99 是直方图桶上界。纳秒时钟的有效分辨率可能更粗，零值不代表零成本。
- 固定到达率场景从计划批次到达到 API 返回的延迟，包含驱动调度和阻塞。它不是写出可见性延迟；未能调用的请求单列，不给它们伪造延迟样本。
- 进程 user+system CPU 时间及每成功记录 CPU 成本，包括驱动、采样、计数和 worker，不能直接称为纯日志库指令开销。
- RSS 为进程高水位，包括运行时、线程及固定直方图；预热后的高水位同时留证，不能从 RSS 直接推导队列占用。
- 排空时间、文件字节数、每秒累计接受数/尝试数/文件大小。监控按秒读取文件大小，可能观察到并发写入中间值。

## 正确性证据

每条日志带 phase、Producer ID 和递增序号。验证器解析所有文件中的所有行，检查精确正文、每 Producer 每阶段严格递增、总数，以及顺序相关和交换律两种 64 位指纹；双文件分别校验。该机制能够发现实际丢失、重复、错序和正文损坏，但指纹不是无碰撞的数学证明。这里核验的是业务正文；原生前缀的所有字段没有另行逐项比较。

任何进程失败或校验失败中止套件，保留失败输出；不以另一次结果静默替换。正常生成的巨大日志默认在校验后删除，保留逐文件 SHA-256、字节数、首尾样本、每 Producer 指纹及完整试验 JSON；可传 `--keep-output` 保留原始全文，需要足够磁盘空间。原始全文删除后，不能离线重新逐行核验；审阅者可以核验留存证据或重新运行。

## 发布边界

当前报告明确标记 Windows/WSL2、CPU、内核、编译器、ext4 和 CPU affinity。未控制 Windows 宿主负载、电源、温度或频率；逻辑 CPU affinity 不是独占物理核心。没有清理全系统页缓存。缓冲文本写入与后台文件系统写回共同作用，结果不能作为物理磁盘带宽或持久化延迟。

本报告可用于公开描述此主机和上述工作负载的实测结果、提交性能回归基线和复现实验。它不代替原生 Linux 部署评测、长时间可靠性验收、多进程/多 Logger 评测、异常磁盘恢复测试或具体业务 SLO 验证。60 秒项目应称为持续负载抽查，不应称为长期稳定性认证。
